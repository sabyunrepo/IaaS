> [페르소나 정의] 역할: 시니어 백엔드 아키텍트, 태도: 핵심 요약 및 리스크 중심의 최종 검토

사용자가 구상 중인 **'특정 유저의 깃 레포지토리 분석 엔진(Verdict)'** 구현을 위한 핵심 내용을 기술적, 전략적으로 종합 정리해 드립니다.

---

### 1. 분석 대상 및 범위 (Public Focus)

* **오가니제이션(Org) 레포:** 유저가 프로필에 **'Public'**으로 설정한 Org의 레포지토리는 접근 가능합니다. 단, Private Org나 관리자가 외부 접근을 차단한 경우는 API로 가져올 수 없습니다.
* **필터링 우선순위:** 데이터 오염을 막기 위해 아래 3가지는 반드시 제외해야 합니다.
* **Fork 레포:** 타인의 코드를 복사해온 것이므로 분석 가치 없음.
* **유령 기여:** 레포 소속 멤버이나 실제 커밋(Code Addition)이 없는 경우.
* **라이브러리/주석:** 수집된 코드 내에서 외부 의존성 코드는 분리 필요.



### 2. 기술적 해결책: GraphQL의 도입

REST API의 한계를 극복하기 위해 **GraphQL** 사용이 필수적입니다.

* **효율성:** REST는 수십 번의 호출이 필요하지만, GraphQL은 **단 1회의 요청**으로 '유저 정보 + 소속 Org + 직접 짠 레포 리스트'를 묶어서 가져옵니다.
* **비용 절감:** GitHub API의 호출 제한(Rate Limit)을 가장 효과적으로 아끼는 방법입니다.
* **정밀도:** 쿼리 단계에서 `isFork: false`와 같은 조건을 걸어 서버 부하를 줄일 수 있습니다.

### 3. 유저 코드 추출 프로세스 (Workflow)

| 단계 | 작업 내용 | 활용 도구/필드 |
| --- | --- | --- |
| **1. 식별** | 유저가 공개한 Org 및 개인 레포 리스트 확보 | GraphQL (`repositories`) |
| **2. 검증** | 포크 여부(`isFork`) 확인 및 유저 이메일 기반 커밋 필터링 | GraphQL (`history`) |
| **3. 추출** | 해당 유저가 작성한 커밋의 `patch` 또는 `diff` 데이터 수집 | REST API (`commits/{sha}`) |
| **4. 정제** | 단순 오타 수정, 주석, 자동 생성 코드(Boilerplate) 제외 | Regex 또는 AST 파싱 |

---

### 4. 시니어의 비판적 제언 (현실적 리스크)

1. **데이터 무결성:** 유저가 Git 설정을 잘못하여 커밋 이메일이 GitHub 계정과 다를 경우, 기여분이 누락될 수 있습니다. 이를 보완하기 위해 유저에게 '분석할 이메일'을 추가로 입력받는 로직이 안전합니다.
2. **API 쿼터 관리:** 아무리 GraphQL을 써도 대규모 분석 시 쿼터가 부족할 수 있습니다. **Redis 같은 캐시 시스템**을 도입하여 동일 유저에 대한 반복 요청을 최소화하십시오.
3. **법적 경계:** '퍼블릭' 코드라 하더라도 이를 상업적 점수로 수치화할 때는 해당 레포의 라이선스(MIT, Apache 등)를 위반하지 않는지 법적 검토가 필요할 수 있습니다.
