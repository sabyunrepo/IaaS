## 1. 제품 개요

### 1.1 제품명

**Jittda Live** (짓다 라이브)

### 1.2 비전

> AI 면접 참모 — 면접관의 인지 부하를 최소화하면서 객관적 평가를 보조한다.

Jittda Live는 면접 전 지원자의 GitHub, 이력서, LinkedIn, 커버레터를 심층 분석하여 Knowledge Graph를 구축하고, 면접 중에는 실시간 음성 인식(STT)과 화자 분리를 통해 대화 맥락을 파악하며, 면접관에게 동적으로 질문을 제안하고, 면접 종료 후 자동 스코어카드를 생성하는 **실시간 AI 면접 가이드 시스템**이다.

### 1.3 타겟 사용자

| 사용자 유형 | 설명 | 핵심 니즈 |
|-------------|------|----------|
| **개발자 면접관** | 시니어/리드 엔지니어로서 기술 면접을 진행하는 인원 | 면접 준비 시간 단축, 지원자 코드 기반 구체적 질문 |
| **비개발자 면접관** | HR, 팀 리더 등 기술 배경 없이 개발자 면접에 참여하는 인원 | 비개발자도 개발자 실력을 객관적으로 판단할 수 있는 가이드 |
| **연속 면접 진행자** | 하루에 3명 이상의 지원자를 연속 평가하는 면접관 | 피로 없는 일관된 평가 기준 유지 |

### 1.4 핵심 가치 제안 (Value Proposition)

**Pre-generated Deck (0ms) + Real-time Probing (trigger-based) 2-Layer 질문 시스템**

| 레이어 | 설명 | 지연 시간 |
|--------|------|----------|
| **Layer 1: Pre-generated Deck** | v5.0 분석 결과 기반, 면접 전 자동 생성된 질문 카드 묶음 | 0ms (사전 생성) |
| **Layer 2: Real-time Probing** | 면접 중 트리거 기반 동적 꼬리 질문 생성 | < 500ms |

| 기존 면접 | Jittda Live |
|-----------|-------------|
| 면접관이 직접 질문 준비 (1-2시간/지원자) | Knowledge Graph 기반 Question Deck 자동 생성 (5분) |
| 면접 중 수기 메모, 핵심 놓침 | 실시간 트랜스크립트 + 토픽 커버리지 자동 추적 |
| 면접 후 기억에 의존한 평가 | 발화 기반 자동 스코어카드 생성 |
| 범용 질문, 실력 판별 어려움 | 지원자 실제 코드에서 추출한 구체적 질문 |
| 비개발자 면접관, 기술 평가 불가 | 비개발자용 답변 가이드 + 전문 용어 설명 |

### F-001: OS 네이티브 오디오 캡처

| 항목 | 내용 |
|------|------|
| **ID** | F-001 |
| **우선순위** | P0 |
| **설명** | 서드파티 드라이버 없이 시스템 오디오 + 마이크를 동시 캡처 |
| **의존성** | Electron 33+, OS 네이티브 API |

**플랫폼별 구현:**

| 플랫폼 | API | 비고 |
|--------|-----|------|
| macOS 13.0+ (Ventura) | ScreenCaptureKit / CoreAudio | 시스템 오디오 권한 필요 |
| Windows 10+ | WASAPI Loopback | 추가 드라이버 불필요 |

**채널 분리 전략:**

```
Mic (면접관 음성) → Left Channel (Ch0)
System Audio (지원자 음성) → Right Channel (Ch1)
Output: Stereo PCM (48kHz, 16bit)
```

**수용 기준 (Acceptance Criteria):**

| # | 기준 | 검증 방법 |
|---|------|----------|
| AC-1 | macOS 13.0+에서 시스템 오디오 캡처 성공 | 수동 테스트: Zoom/Meet 통화 음성 캡처 확인 |
| AC-2 | Windows 10+에서 WASAPI 루프백 캡처 성공 | 수동 테스트: Teams/Meet 통화 음성 캡처 확인 |
| AC-3 | 스테레오 PCM 출력 (48kHz, 16bit) | 자동화 테스트: 출력 포맷 검증 |
| AC-4 | 채널 분리 정확도 — Mic=Ch0, System=Ch1 | 자동화 테스트: 채널별 독립 신호 확인 |
| AC-5 | 캡처 시작/중지 제어 가능 | UI 테스트: 녹음 버튼 동작 확인 |

### F-002: 엣지 기반 VAD (Voice Activity Detection)

| 항목 | 내용 |
|------|------|
| **ID** | F-002 |
| **우선순위** | P0 |
| **설명** | 브라우저/Electron에서 실행되는 경량 음성 활동 감지 |
| **기술** | Silero VAD (WASM) — `@ricky0123/vad` |
| **의존성** | F-001 (오디오 캡처) |

**핵심 파라미터:**

| 파라미터 | 값 | 설명 |
|----------|-----|------|
| 무음 임계값 | 1.5초 | 무음 1.5초 이상 시 발화 종료로 인식 |
| 추론 레이턴시 | < 1ms | WASM 기반 엣지 추론 |
| 실행 환경 | Client-side (WASM) | 서버 전송 없이 로컬 처리 |

**수용 기준 (Acceptance Criteria):**

| # | 기준 | 검증 방법 |
|---|------|----------|
| AC-1 | VAD 정확도 95% 이상 | 테스트 오디오 샘플 100개 기준 |
| AC-2 | CPU 사용률 5% 미만 | 프로파일링: 면접 30분 동안 평균 CPU 모니터링 |
| AC-3 | 발화 종료 감지 지연 < 200ms | 타임스탬프 비교 테스트 |
| AC-4 | 채널별 독립 VAD 처리 | Ch0/Ch1 각각 독립 발화 감지 확인 |

### F-003: 실시간 STT (Speech-to-Text)

| 항목 | 내용 |
|------|------|
| **ID** | F-003 |
| **우선순위** | P0 |
| **설명** | 실시간 음성-텍스트 변환. 채널별 독립 전사로 면접관/지원자 분리 |
| **기술** | Deepgram Nova-3 Streaming API |
| **의존성** | F-001 (오디오), F-002 (VAD) |

**핵심 사양:**

| 항목 | 값 |
|------|-----|
| 모델 | Deepgram Nova-3 |
| 프로토콜 | WebSocket Streaming |
| 채널 모드 | Multi-channel (면접관 Ch0 / 지원자 Ch1) |
| 한국어 WER | 7-16% (Deepgram 공식) |
| Interim 결과 | 실시간 표시 (확정 전 회색 텍스트) |
| Final 결과 | 500ms 이내 확정 |

**수용 기준 (Acceptance Criteria):**

| # | 기준 | 검증 방법 |
|---|------|----------|
| AC-1 | 실시간 전사 UI 표시 (Interim + Final) | E2E 테스트: 음성 입력 후 텍스트 표시 확인 |
| AC-2 | Final 결과 500ms 이내 도달 | 레이턴시 측정: VAD 종료 → Final 전사 타임스탬프 |
| AC-3 | 채널별 독립 전사 (면접관/지원자 분리) | 테스트: 두 화자 동시 발화 시 분리 확인 |
| AC-4 | 한국어 전사 지원 | 한국어 샘플 10개 이상 전사 정확도 확인 |
| AC-5 | WebSocket 연결 끊김 시 자동 재연결 | 네트워크 차단 후 복구 테스트 |

| AC-3 | 오프라인 동작 확인 | 네트워크 차단 상태에서 검색 성공 확인 |
| AC-4 | 벡터 데이터 동기화 완료 후 검색 가능 | 동기화 → 즉시 검색 가능 여부 확인 |

### F-005: Knowledge Graph 동기화

| 항목 | 내용 |
|------|------|
| **ID** | F-005 |
| **우선순위** | P0 |
| **설명** | 서버에서 구축된 Knowledge Graph를 JSON으로 직렬화 후 Electron 클라이언트로 동기화 |
| **기술** | graphology 0.25+ (Client), NetworkX 3.4+ (Server) |
| **의존성** | v5.0 분석 파이프라인 완료 |

**동기화 흐름:**

```
[Server: NetworkX 3.4+]
  ↓ JSON 직렬화
[Transfer: HTTP/S3]
  ↓ 다운로드
[Client: graphology 0.25+]
  ↓ 인메모리 로드
[탐색: < 5ms]
```

**수용 기준 (Acceptance Criteria):**

| # | 기준 | 검증 방법 |
|---|------|----------|
| AC-1 | KG JSON 로드 시간 < 2초 | 벤치마크: 노드 5000개 기준 로드 시간 측정 |
| AC-2 | 그래프 탐색 < 5ms | 벤치마크: BFS/DFS 탐색 P95 레이턴시 |
| AC-3 | 서버 KG와 클라이언트 KG 데이터 일치 | 해시 비교: 노드/엣지 수 및 속성 검증 |
| AC-4 | 동기화 실패 시 이전 버전 유지 (Fallback) | 동기화 중 네트워크 차단 후 기존 KG 유지 확인 |

### F-006: Pre-generated Question Deck

| 항목 | 내용 |
|------|------|
| **ID** | F-006 |
| **우선순위** | P0 |
| **설명** | v5.0 분석 완료 후 자동 생성되는 질문 카드 묶음 (Layer 1) |
| **의존성** | v5.0 분석 파이프라인, F-005 (KG) |

**질문 카드 구조:**

```json
{
  "id": "QD-001",
  "category": "기술",
  "subcategory": "아키텍처",
  "text": "이 프로젝트에서 Repository 패턴을 사용하신 이유는 무엇인가요?",
  "intent": "지원자의 설계 의사결정 능력 평가",
  "expected_answer": "데이터 접근 계층을 추상화하여...",
  "verification_points": ["추상화 이해", "테스트 용이성 인지", "실제 적용 경험"],
  "follow_up_candidates": ["QD-002", "QD-007"],
  "difficulty": "중",
  "source": "github:repo/src/repositories/user_repo.py",
  "non_dev_guide": "이 질문은 지원자가 코드를 체계적으로 정리하는 능력을 확인합니다."
}
```

**카테고리 분류:**

| 카테고리 | 설명 | 최소 질문 수 |
|----------|------|-------------|
| 기술 (Technical) | 코드, 아키텍처, 알고리즘, 설계 패턴 | 5개 |
| 행동 (Behavioral) | 협업, 갈등 해결, 리더십 | 3개 |
| 상황 (Situational) | 가상 시나리오 기반 문제 해결 | 3개 |
| 프로젝트 (Project) | 지원자 실제 프로젝트 기반 질문 | 4개 |

**수용 기준 (Acceptance Criteria):**

| # | 기준 | 검증 방법 |
|---|------|----------|
| AC-1 | 최소 15개 질문 생성 | 분석 완료 후 Deck 카드 수 확인 |
| AC-2 | 카테고리 4개 이상 충족 | 카테고리별 분포 확인 |
| AC-3 | 각 질문에 의도/예상답변/검증포인트 포함 | 스키마 검증 |
| AC-4 | 비개발자용 가이드 포함 | `non_dev_guide` 필드 존재 및 가독성 확인 |
| AC-5 | 네트워크 없이 Deck 조회 가능 (Local-First) | 오프라인 상태에서 Deck 표시 확인 |

### F-007: 실시간 꼬리 질문 생성

| 항목 | 내용 |
|------|------|
| **ID** | F-007 |
| **우선순위** | P0 |
| **설명** | 면접 중 트리거 기반으로 동적 꼬리 질문을 실시간 생성 (Layer 2) |
| **기술** | Groq (Llama 3.3 70B) |
| **의존성** | F-003 (STT), F-004 (벡터 검색), F-005 (KG), F-006 (Deck) |

**트리거 조건:**

| 트리거 | 설명 | 우선순위 |
|--------|------|---------|
| 이력서 모순 감지 | STT 발화와 이력서/KG 데이터 불일치 | 높음 (빨강) |
| 모호 답변 감지 | 구체성 부족, 핵심 회피 패턴 | 높음 (빨강) |

**출력 사양:**

| 항목 | 값 |
|------|-----|
| 생성 질문 수 | 최대 3개 |
| 각 질문 구성 | 질문 텍스트 + 목적 간략 표시 |
| 생성 시간 | < 500ms |
| 모델 | Groq Llama 3.3 70B (추론 최적화) |

**수용 기준 (Acceptance Criteria):**

| # | 기준 | 검증 방법 |
|---|------|----------|
| AC-1 | 질문 생성 시간 < 500ms | 타임스탬프 측정: 트리거 발생 → 질문 표시 |
| AC-2 | 생성된 질문 관련성 80% 이상 | 면접관 피드백 수집 (관련/비관련 태깅) |
| AC-3 | 트리거 4가지 유형 모두 동작 | 각 트리거별 시나리오 테스트 |
| AC-4 | 질문 3개 이내 제한 | 출력 검증: 4개 이상 생성 불가 확인 |
| AC-5 | Groq API 장애 시 Deck 질문으로 폴백 | API 차단 후 Deck 질문 제시 확인 |

### F-008: 토픽 커버리지 추적

| 항목 | 내용 |
|------|------|
| **ID** | F-008 |
| **우선순위** | P0 |
| **설명** | JD 역량 요소별 검증 상태를 실시간 추적 |
| **의존성** | F-003 (STT), F-005 (KG) |

**추적 메커니즘:**

```
JD 역량 요소 목록 (예: React, 시스템 설계, 팀 리더십, ...)
  ↓ STT 전사 텍스트 + KG 매핑
```

| 통신 | 전 구간 암호화 | HTTPS/WSS 전용 (HTTP/WS 리다이렉트) |
| 개인정보 | 민감 데이터 로컬 우선 처리 | Local-First 원칙 (면접 음성은 서버 미전송) |
| API 키 | 클라이언트 노출 방지 | Electron Main Process에서만 API 키 접근 |
| CORS | 허용 오리진 제한 | 화이트리스트 기반 |

### 4.3 안정성 요구사항

| 영역 | 요구사항 | 구현 |
|------|---------|------|
| 에러 모니터링 | 실시간 에러 수집/알림 | Sentry self-hosted |
| 로깅 | 구조화된 로그 | structlog (Python) |
| 요청 추적 | 분산 추적 | 상관 ID (UUID v7) 기반 |
| 오프라인 폴백 | 네트워크 없이 기본 기능 동작 | Deck 질문은 로컬에서 표시 가능 |
| 재연결 | WebSocket 끊김 자동 복구 | Exponential backoff 재연결 |
| 데이터 보존 | 면접 중 크래시 시 데이터 손실 방지 | 전사본 주기적 로컬 저장 (30초 간격) |

## 부록 A: 용어 사전

| 용어 | 설명 |
|------|------|
| **Deck** | 면접 전 사전 생성된 질문 카드 묶음 (Layer 1) |
| **Probing** | 면접 중 트리거 기반 실시간 질문 생성 (Layer 2) |
| **Knowledge Graph (KG)** | 지원자의 GitHub, 이력서, LinkedIn 데이터를 연결한 지식 그래프 |
| **VAD** | Voice Activity Detection — 음성 활동 감지 |
| **STT** | Speech-to-Text — 음성-텍스트 변환 |
| **WER** | Word Error Rate — 단어 오류율 (낮을수록 좋음) |
| **Local-First** | 서버 연결 없이 클라이언트에서 우선 처리하는 아키텍처 원칙 |
| **HMAS** | Hierarchical Multi-Agent System — 계층적 멀티 에이전트 시스템 |
| **ErrorPrism** | 에러 체인 추적 시스템 (연관 에러를 상관 ID로 묶어 추적) |
| **E2E 레이턴시** | 오디오 입력 → 질문 카드 표시까지의 전체 지연 시간 |
